# Gitops Spec

The `gitups gitops *` command group is the post-provisioning concern of the
gitups CLI. It turns a declarative *package set* into rendered git repos and
bootstraps a target cluster with the KRC/SRC controllers that own ongoing
reconciliation. This spec is the source of truth for the gitops kinds, the
two-stage flow, the catalog source drivers, and the rules render and apply
must follow.

## Kinds

`apiVersion: gitups.io/v1alpha1`

| Kind | Owns |
| --- | --- |
| `GitOpsPackageSet` | User-authored intent: catalog sources, output repositories, package selections, controller assignment, capability bindings. |
| `FullGitOpsPackageSet` | Generated by `gitups gitops expand`. Reviewable, idempotent, placeholder-bearing; the user fills placeholders here before render. |
| `PackageDefinition` | Per-package descriptor authored in the catalog (`packages/<name>/package.yaml`). Loaded by the catalog driver; never written by gitups. |

`GitOpsPackageSet` and `FullGitOpsPackageSet` are **peer authoring artifacts**.
They are not members of the cluster-infra `State` aggregate
([state-model.md](state-model.md)). Loaders are split: cluster-infra kinds
are consumed by `internal/infra/LoadNormalizeValidate`; gitops kinds by
`internal/gitops/load.LoadGitOpsPackageSet` /
`LoadFullGitOpsPackageSet`.

## Non-Negotiable Invariants

1. **Two-stage flow.** `GitOpsPackageSet` (user-authored) → `FullGitOpsPackageSet`
   (expanded, reviewable, placeholder-bearing) → rendered repo dirs. Render
   reads only `FullGitOpsPackageSet`, never the input form.
2. **Lean input.** `GitOpsPackageSet.spec` carries only sources, repositories,
   selected templates, controllers, and bindings. Defaults and inferable
   fields belong in `package.yaml`.
3. **Install vs resources.** A package is one service/application. It declares
   install methods under `install/<renderer>/descriptor.yaml` and optional
   custom resources under `resources/<resourceTemplate>/descriptor.yaml`.
   Generic repositories select installs; env repositories select or derive
   resources.
4. **`FullGitOpsPackageSet` is authoritative.** Re-expand is idempotent and
   preserves user edits. The placeholder sentinel is `__GITUPS_PLACEHOLDER__`
   (`v1.PlaceholderSentinel`); it does not change.
5. **No target-cluster metadata in the schema.** `GitOpsPackageSet` and
   `FullGitOpsPackageSet` must work for multiple clusters. Runtime context is
   supplied by CLI flags (`--context`, `--to`).
6. **Renderer priority OLM → Kustomize → Helm → raw.** Apply when choosing an
   install method and when picking the renderer for a resource descriptor.
7. **Repositories are user intent.** `spec.repositories[]` is the only source
   of output repo placement. Package descriptors do not declare `targetRepo`.
8. **Controllers are first-class.** Every package declares
   `role: kubernetes-resource-controller | service-resource-controller | workload`.
   `spec.controllers.{kubernetesResources,serviceResources}` assigns KRC/SRC
   roles to selected package instances.
9. **Prefer KRC over SRC.** When desired state can be expressed as K8s CRs,
   route it through the KRC. Reach for SRC only when the target has no stable
   CR (service-level admin APIs, external SaaS, controller-specific bundles).
10. **Capabilities are open extension points.** Packages declare
    `provides[]` / `requires[]` with free-form capability names. Core enforces
    shape (non-empty fields, unique names, consistent provider/consumer
    wiring) but does not hold a closed list.
11. **Hook ABI is stable.** Hooks are invoked as
    `<script> --phase <phase> --values <json-path> --out <render-dir>` and
    may write only inside `--out`.
12. **Generation is deterministic and hermetic.** Same inputs produce
    identical bytes. No timestamps, random IDs, or network calls during
    render except pinned `helm template --repo` chart pulls.
13. **Pin everything.** Chart versions, `startingCSV`, catalog sources,
    image tags, and upstream URLs must be exact. Never `latest` or floating
    ranges.
14. **Cluster access is explicit and KRC-declared.** `apply` is the only
    mutating cluster command. Gitups carries no hard-coded cluster binary.
    The selected KRC's `spec.cli.binary` and per-intent arg templates drive
    everything (`apply`, `apply-dry-run`, `get-json`, `wait-condition`,
    `wait-crds-established`, `list-crds`, `server-version`, `list-pods-jsonpath`,
    `pod-logs`).
15. **Push is the only outbound mutating command.** Talks to a git provider
    (GitHub, GitLab, Gitea) to create missing repos and publish trees.
    Reuses the user's git credential helpers by default; `--token`, `--user`,
    `--base-url` override per invocation. Secrets are read from flags/env
    only, never from `GitOpsPackageSet`, `FullGitOpsPackageSet`, or rendered
    trees.

## Catalog source drivers

`spec.sources[]` discriminates by structural sub-block. Exactly one of
`filesystem`, `oci`, or `git` must be set per source (R3 — no `type`/`mode`
strings).

```yaml
sources:
  - name: local
    filesystem:
      path: ../../../../../gitops-workspace/gitups-packages/packages
  - name: stable
    oci:
      registry: ghcr.io/crmarques/gitups-packages
      digest: sha256:abc...           # pin by digest, not tag
  - name: pinned-fork
    git:
      url: https://github.com/example/gitups-packages.git
      ref: pkg/keycloak/v0.1.0        # tag or commit SHA; branches rejected
      path: packages
```

Driver semantics:

- **filesystem** — Resolved relative to the GitOpsPackageSet file. No cache.
- **oci** — Per-package artifact pull via `oras`. Cache key
  `(registry, tag|digest)`. Pulls
  `<registry>/<package-name>:<tag>` (or `@<digest>`) for each package the
  set references. Cache lives at `<state-dir>/gitops/sources/oci/<encoded-ref>/`.
- **git** — Shallow clone at `ref`. Cache key `(url, ref)`. Branch refs are
  rejected (mutable). Cache lives at
  `<state-dir>/gitops/sources/git/<encoded-url>/<ref>/`.

All drivers ultimately produce a filesystem path the catalog walker reads.

## Workspace + state-dir model

| Artifact | Location | Why |
| --- | --- | --- |
| `gitops-package-set.yaml` (synonym: `provision.yaml`) | `<workspace>/<name>/` (user-tracked) | Authored input |
| `full-gitops-package-set.yaml` (synonym: `full-provision.yaml`) | `<workspace>/<name>/` (user-tracked) | Reviewed output, placeholder edits live here |
| OCI/git source caches | `<state-dir>/gitops/sources/...` | Pure derivative; safe to delete |
| Rendered repo trees | `<state-dir>/gitops/<name>/repos/` (cache) | Pure derivative |
| Apply intent logs / lock | `<state-dir>/gitops/<name>/apply/` (cache) | Pure derivative |

Authoring artifacts go where the user puts them (default workspace
`./gitops-workspaces/<name>/`). Caches go under `--state-dir`.

## CLI

The `gitops` group is a peer of `provider` and `clusters`. Verbs are not the
ansible-shaped scope verbs; they preserve the upstream gitops vocabulary:

```text
gitups gitops init <name>            # scaffold a GitOpsPackageSet workspace
gitups gitops expand <name>          # GitOpsPackageSet -> FullGitOpsPackageSet
gitups gitops check <name>           # validate (read-only, no host preflight)
gitups gitops render <name>          # FullGitOpsPackageSet -> repo trees
gitups gitops fill <name>            # interactive placeholder filler
gitups gitops plan <name>            # print apply plan
gitups gitops push <name>            # publish rendered repos
gitups gitops apply <name>           # expand -> render -> push -> bootstrap
gitups gitops wait <name>            # poll cluster state
gitups gitops status <name>          # drift + freshness report
gitups gitops destroy <name>         # tear down bootstrap
```

The `generate` verb from the upstream CLI is renamed to `render` to remove
semantic adjacency to `gitups secrets generate`. `destroy` is new and is
currently advisory: it prints the manual `kubectl delete` commands until KRC
packages declare a destroy intent.

## Anti-Goals

- Not a Kubernetes controller; gitops does not watch or reconcile in-cluster.
- Not a Helm/Kustomize/OLM replacement; it orchestrates them.
- Not a secrets manager; secrets surface as placeholders. `gitups gitops apply
  --generate-secrets` may fill placeholders whose input declared a `generator`
  block at apply time only — never during render — so render stays
  deterministic.
- Not a general-purpose templating engine; Go templates stay limited to small
  values and overlay wrappers.
